# Matriz de trazabilidad de restricciones (R001–R102)

Relaciona las 102 restricciones del modelo técnico aprobado con el lugar donde se garantizan:
la base de datos (`db/01_schema.sql`) o la capa de negocio en Java.

## Cómo leer la matriz

- **SQL**: la base lo garantiza por sí sola. Se nombra la restricción (`ck_`, `uq_`, `fk_`), el
  disparador (`tg_`) o la regla que este rechaza (`rg_`, que llega a Java en el campo *constraint*
  del error, con SQLSTATE `P0001`).
- **Negocio**: la base no puede garantizarlo con fiabilidad (depende de sumas sobre varias filas,
  de bloqueos, del rol vigente de quien opera, de la fecha actual o de sistemas externos). Lo debe
  garantizar el servicio indicado, dentro de la transacción de la operación.
- **SQL + Negocio**: la base impone una parte (normalmente la coherencia de la fila, la unicidad o la
  inmutabilidad) y el servicio el resto. La columna «Negocio» dice qué queda a cargo de Java.

Los nombres de la columna «Negocio» son clases y métodos reales de `src/main/java/com/feder/negocio`
(verificados contra el código). Las filas marcadas «PARCIAL» o «Pendiente» en la última columna indican lo que
el código aún no cubre.

Criterio aplicado a los disparadores: solo protegen datos que se fijan y no cambian, la coherencia
entre filas cuyos datos comparados son inmutables o finales, y las reglas para las que el modelo
indica expresamente un disparador. No implementan procesos (reservas, máquinas de estados, totales).

## Condiciones que el esquema impone a la capa de negocio

1. **Saldo y estado del lote en una sola sentencia.** `ck_lote_feder_agotado_sin_saldo` exige que un
   lote no BLOQUEADO ni VENCIDO esté AGOTADO si y solo si su saldo es 0. El `UPDATE` que deja el
   saldo en 0 (o lo saca de 0) debe cambiar `estado` en la misma sentencia.
2. **Registro de recepción en bitácora.** Para `entidad = 'DETALLE_COMPRA'` con `operacion`
   `RECEPCION` o `CANCELACION`, `detalle` debe traer `clave_operacion`, `compra_id` y `entidad_id`; la
   recepción trae además `cantidad_aceptada` como número JSON (`ck_bitacora_operacion_detalle_compra`).
   Esa clave es la que usa `rg_detalle_compra_precio_fijo`.
3. **Orden dentro de la transacción.** El reembolso sin devolución se inserta después de pasar el
   pedido a CANCELADO; la devolución que rectifica se inserta después de anular la equivocada; el
   movimiento `ENTRADA_RETORNO_ENTREGA` se inserta con la reserva ya CONSUMIDA.
4. **Datos que no se modifican con UPDATE.** Línea de pedido (producto, cantidad, precio, subtotal,
   descripción), reserva (lote, línea, cantidad), reembolso (pago, devolución, monto, clave), tipo del
   pedido, pedido de un pago, productor de una compra, origen de un detalle de compra, detalle de un
   lote de FEDER, producción y código de un lote de origen, comunidad de origen de una producción.
   Los movimientos de inventario y la bitácora no admiten `UPDATE` ni `DELETE`.
5. **Borrado restringido.** Con `ON DELETE RESTRICT`, PostgreSQL 18 devuelve SQLSTATE `23001`;
   las versiones anteriores, `23503`. La traducción de errores debe tratar ambos como clave foránea.

## Multiplicidades mínimas de las asociaciones

Las multiplicidades `1..*` y `1` del extremo dependiente (toda cuenta con al menos una concesión, toda
compra con al menos un detalle, todo pedido con al menos una línea, un registro de historial y
exactamente una entrega, todo lote de FEDER con su ENTRADA_COMPRA) no son declarables con claves
foráneas. Las garantiza el servicio que crea el agregado en una sola transacción
(`ServicioCuentas.registrarCliente`, `ServicioCompras.registrarCompra`, `ConfirmacionCarrito.confirmar`,
`ServicioRecepcion.recibir`). `verificar_semilla.sql` las comprueba sobre los datos cargados.
